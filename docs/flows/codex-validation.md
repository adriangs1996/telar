# Codex integration validation

This comparison uses T3 Code commit
[`9375c779707fb95c06670db6da87441720b2d2e2`](https://github.com/pingdotgg/t3code/tree/9375c779707fb95c06670db6da87441720b2d2e2)
and the [official app-server documentation](https://learn.chatgpt.com/docs/app-server).
The local protocol probe used Codex CLI 0.154.0. Model availability and effort
choices below describe that account and that run.

## Protocol and T3 comparison

| Concern | T3 Code at the pinned commit | Telar |
| --- | --- | --- |
| Process and authentication | Starts a piped app-server with inherited environment and an optional configured `CODEX_HOME`; probes `account/read`. | The runtime starts `codex app-server --listen stdio://`. It inherits the installed CLI's authentication environment, including `CODEX_HOME`, and removes `TELAR_*` authority variables. No separate login UI or account probe. |
| Initialization | Sends `initialize` with client metadata and `experimentalApi: true`, followed by `initialized`. | Sends the same handshake without experimental API opt-in. |
| Model discovery | Follows `model/list` pagination and maps each model's supported efforts into picker options. | Requests the first 16 visible models. Each model carries at most eight effort identifiers. A remaining page produces a visible notice. |
| Turn settings | Passes selected model and effort alongside approval and sandbox settings to `turn/start`. | Every prompt carries its copied draft model, effort and access choice. Runtime and provider validate the model/effort pair against the catalog before starting the turn. |

[effort mapping](https://github.com/pingdotgg/t3code/blob/9375c779707fb95c06670db6da87441720b2d2e2/apps/server/src/provider/Layers/CodexProvider.ts#L148),
and [turn parameters](https://github.com/pingdotgg/t3code/blob/9375c779707fb95c06670db6da87441720b2d2e2/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L608).
Telar sources: [Session.zig](../../src/backend/agent_panes/Session.zig),
[Codex.zig](../../src/backend/agent_panes/Codex.zig), and
[model_catalog.zig](../../src/backend/agent_panes/model_catalog.zig).

The official API specifies the initialization handshake, model discovery and
turn overrides. Experimental opt-in enables additional methods and fields;
Telar's implemented requests do not require it. Efforts remain bounded strings,
so a provider can advertise values such as `max` or `ultra` without a Telar enum
change. The catalog default effort and the effective thread effort can differ.
Telar keeps returned thread settings when the current catalog supports them.
If the configured model is absent, it selects the provider's marked default
model and default effort for the next turn, or the first listed model when none
is marked. An unsupported effort also falls back to the selected model's
advertised default. Both substitutions produce a system notice; the catalog
contains only capabilities returned by Codex.
[Official protocol reference](https://learn.chatgpt.com/docs/app-server#experimental-api-opt-in).

## Conversation semantics

The conversation design uses T3's distinction between assistant prose, compact
activity rows and subagent cards. Active text highlights use Telar's coalesced
frame clock and stop requesting work when hidden or complete.
[T3 message timeline](https://github.com/pingdotgg/t3code/blob/9375c779707fb95c06670db6da87441720b2d2e2/apps/web/src/components/chat/MessagesTimeline.tsx).

The adapter was checked against the JSON schemas generated by Codex CLI 0.154.0.
It normalizes message phase, command/file/MCP/dynamic-tool status, public
reasoning summaries, plans and `collabAgentToolCall` into typed items. It records
child identity only from explicit collaboration, `subAgentActivity` or
`thread/started` spawn metadata. Unrelated thread notifications cannot become
children of the active conversation.

Dispatch completion and child completion are separate events. A completed child
turn leaves the child Idle and available for further work. Child output does
not enter the parent's assistant message. These semantics follow T3's Codex
adapter and the installed provider schema, with bounded local retention.
[T3 Codex adapter](https://github.com/pingdotgg/t3code/blob/9375c779707fb95c06670db6da87441720b2d2e2/apps/server/src/provider/Layers/CodexAdapter.ts).

## Permissions

Telar starts each new thread with `workspace-write`, `untrusted` approvals and
the `user` reviewer. Subsequent turns send explicit settings:

| Composer access | `sandboxPolicy.type` | `approvalPolicy` |
| --- | --- | --- |
| Read only | `readOnly` | `untrusted` |
| Workspace | `workspaceWrite` | `untrusted` |
| Full access | `dangerFullAccess` | `never` |

The reviewer remains `user`. Read-only and workspace turns explicitly disable
network access in their sandbox policy. These choices affect the pane's turns;
Telar does not write global Codex configuration.

T3's `auto-accept-edits` uses `on-request` with `workspace-write`. Its `auto` mode
uses the automatic reviewer. Telar currently exposes neither mapping.
[T3 permission mapping](https://github.com/pingdotgg/t3code/blob/9375c779707fb95c06670db6da87441720b2d2e2/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L509).

## Direct protocol proof

Local evidence: `/tmp/telar-codex-live-jkjsju9s/result.json`.
This probe called the installed app-server directly with inherited CLI
authentication, outside Telar's runtime and GUI.

- Completed `initialize`, `initialized`, `model/list`, `thread/start` and
  `turn/start`, without experimental API opt-in.
- Received five models and no next catalog page.
- Recorded effective thread settings of `gpt-5.6-sol`, effort `max`, read-only
  sandbox, `never` approvals and no network access.
- Explicitly requested `gpt-5.6-sol` with effort `low` for the turn. The streamed
  response was `TELAR_CODEX_OK`; the turn completed and captured no tool
  invocations.
- Reaped the provider process with exit code 0.

The recorded thread settings precede the explicit turn override. This probe
establishes that the installed CLI, authentication and protocol calls work.
Its permission setup differs from Telar's initial workspace policy.

## Telar GUI validation

Local evidence: `/tmp/telar-live-ui-03/result.json` and its `composer.png`,
`models.png`, `draft.png` and `completed.png` screenshots.

The native GUI completed a real turn through Telar IPC, the runtime-owned
`Session` and Codex CLI 0.154.0. The catalog contained five models. The composer
selected `gpt-5.6-terra`, effort `low` and Read only access; the response was
`TELAR_GUI_CODEX_OK`. The run captured no tool items, reused the same provider
after reconnecting, and reaped it after stopping the isolated runtime.

On macOS, reproduce this check with an authenticated installed CLI:

```sh
python3 tools/gui_agent_live.py zig-out/bin/telar /tmp/telar-codex-check --codex /absolute/path/to/codex
```

The output directory must be new. This makes one real model call in read-only
mode. Its forwarding process passes app-server messages unchanged and records
only the catalog, requested turn settings, completion and process lifecycle.
It does not record authentication responses.

The composer also passed a native layout check at window widths of 1200, 660
and 420 points. That run used a simulated provider and verified model, effort
and permission choices in the outgoing turn. Its screenshots and result are
in `/tmp/telar-composer-native-04/`. This visual check is separate from the real
Codex turn above.

The final simulated-provider lifecycle run is recorded in
`/tmp/telar-composer-lifecycle-01/result.json`. It verifies native `prefix + a`,
multiline submission, completion while the GUI is detached and reconnection to
the same provider. The provider was reaped when the isolated runtime stopped.

A separate startup check with the bundled CLI `0.151.0-alpha.7.2` returned a
configured `gpt-6-astra` thread while its catalog omitted that model. Provider
regressions cover this mismatch, both response orders, fallback to the marked
catalog default and unsupported configured efforts. The completed GUI evidence
above applies to CLI 0.154.0; it does not establish a completed turn on the older
bundled version.


## History pagination validation

The history reader was checked against the same installed CLI 0.154.0 and the
persisted thread from the real GUI check above. It initialized a separate
app-server, read thread metadata and traversed the two stored messages with
`thread/items/list`. Following an earlier and a later cursor returned the
expected message with the same provider turn and item IDs. This check made no
model calls and
did not resume or change the thread. Local evidence is in
`/tmp/telar-history-live-provider-turn.log`.

The provider's backwards cursor includes its anchor. Telar wraps that cursor
with its turn and item IDs and an exclusive byte boundary so reversing direction
does not duplicate a message or text fragment. Simulated-provider tests traverse 100 messages in
both directions, reconstruct a 128 KiB UTF-8 message from fragments, and check
empty items, oversized output, unsupported legacy storage, timeout and
cancellation. The subprocess must be reaped on success and failure.

The runtime IPC regression repeats navigation from two independent attached
clients and checks that page replies never replace the live snapshot. Items with
the same ID in distinct turns remain separate, including when used as the
initial reading anchor. History
uses an experimental provider API; unsupported storage produces an explicit
error rather than presenting a truncated conversation as complete.

## Pagination and selection regression validation

The combined `test test-gui check codestyle check-client-boundaries` run passed
4,113 tests with two skipped and completed all 167 build steps. Local evidence
is in `/tmp/telar-pagination-interaction-final.log`. These GUI tests run headless;
this run did not repeat the native visual checks below or restart user sessions.

Selection regressions cover dragging across formatted messages and code,
autoscrolling without new pointer events, resizing, live updates, stale frames,
focus changes, pinned history pages and the 64 KiB clipboard limit. Keyboard
regressions cover configurable copy-mode entry, cursor navigation, selection,
Tab and Escape, and failed or delayed clipboard acknowledgements. Composer
tests also reject stale paste and cut completions after edits or focus changes.

## Conversation rendering validation

`tools/gui_agent_messages.py` drives native controls against an isolated runtime
and a deterministic app-server fixture. The fixture uses the installed CLI's
public item shapes and deliberately sends child discovery before dispatch. It
covers public reasoning summaries, independent child turns, command output, an
MCP failure, file diffs, final Markdown, disclosure controls and clipboard copy.
Reconnection must retain the conversation with a single provider initialization.
This is a protocol and GUI regression test; it makes no model calls.

On macOS:

```sh
python3 tools/gui_agent_messages.py zig-out/bin/telar /tmp/telar-messages-check
```

The output directory must be new. Optional `--resize WIDTH HEIGHT` also captures
a narrow layout when the window manager permits the requested size. Local visual
evidence is in `/tmp/telar-messages-native-03/result.json`, with separate thinking,
working, subagent, command, diff, final-response and reconnect screenshots.

GUI regressions exercise streamed changes between displayed geometry and a click,
failed frame delivery, superseding scroll gestures, replaced attachments, copy
acknowledgements and offscreen animation. A 48 KiB Markdown document with thousands
of blocks must render its visible viewport within a 96-quad test budget; hidden
rules, list markers and code cards cannot consume that budget.

The local ReleaseFast run in `/tmp/telar-message-final-release.log` measured a
warm frame with a retained 48 KiB response, including transcript measurement,
visible painting and an animated status label. At viewport widths of 160 and
640 points, ASCII took 206–213 microseconds and CJK took 185–281 microseconds.
These are local warm-frame samples, not cold-layout or end-to-end latency
guarantees. The bounded layout cache retains geometry and source offsets;
regressions compare cached output against uncached output and invalidate it
across snapshot, attachment, viewport and font changes.

The final GUI suites passed 445 tests in both Debug and ReleaseFast. The general
`test check check-client-boundaries codestyle` run passed 3,499 tests with two
skipped, and `install codestyle` completed all 48 build steps. Logs are in
`/tmp/telar-message-final-gui.log`, `/tmp/telar-message-final-release.log`,
`/tmp/telar-messaging-final-core.log` and `/tmp/telar-messaging-install-final.log`.
