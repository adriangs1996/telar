# HTTP/1 fuzz targets

Two native Zig fuzz targets test telar's own HTTP/1 relay in memory. They
never open a socket, a listener, a certificate or a real proxy. Every input
is synthetic, with fictitious hosts (`example.test`) and small bodies. The
relay under test is `lib/httprelay/http1`. The session is its own
`FakeSession`, which scripts both sides with fixed buffers, `max_read_bytes`
and `fail_write_at`.

These are robustness and regression tests. They check that the relay keeps
the contracts its source and unit tests already state. They do not propose a
new HTTP policy, and a head the current code admits is admitted by the oracle
too.

## Files

| File | Holds |
| --- | --- |
| `lib/httprelay/http1/head_fuzz_test.zig` | the head target: `relayHead`, which reads, reports, forwards and analyzes one head |
| `lib/httprelay/http1/body_fuzz_test.zig` | the body target: `relayBody` under every body plan |
| `lib/httprelay/http1/fuzz_corpus.zig` | encodes typed seeds in `std.testing.Smith`'s input form at compile time |
| `lib/httprelay/http1/ByteEdit.zig` | one replace, insert, delete or CRLF insertion applied to generated bytes |
| `build/fuzz_http1.zig` | registers `test-fuzz-http1`, `test-fuzz-http1-head` and `test-fuzz-http1-body` |

Each target is its own test root and imports the `httprelay` library module
that `build/Libraries.zig` already builds. No file here is imported by
`lib/httprelay/root.zig`, a suite or the coverage build, so none of them
compiles a `std.testing.fuzz` call. Nothing in production is exported for
these tests. The targets reach the relay through `http1.relayHead`,
`http1.relayBody`, `http1.FakeSession`, `http1.max_head_bytes` and
`http1.max_chunk_line_bytes`, all public already. The output bound comes from
the size of `FakeSession`'s output array, which is
`test_support.max_output_bytes`.

Only each target's own root drops error return traces, because Zig 0.16.0's
runner does not compile its fuzz loop with them. Runtime safety stays on, the
artifact uses LLVM, and the relay keeps the library module every other graph
builds.

## Head contracts

`fuzz generated heads` draws a `HeadShape` with `Smith.value`: request or
response, method, target, status and reason, up to 8 fields, a padding field,
how the input ends, a read limit and whether the write fails. The fields cover
`Content-Length` (single, repeated, leading zeros, mismatched, trailing comma,
empty, a word), `Transfer-Encoding` (`chunked`, `CHUNKED`, `gzip, chunked`,
`gzip`, `chunked, gzip`, empty, an empty member), `Connection`,
`Content-Type` (SSE with and without parameters, JSON), `Content-Encoding`,
`Host` and a filler. Each field name gets a case mask and one of three
spacings around its value.

The oracle reads the shape and never parses the bytes. It gathers what the
fields declare and derives the framing, status, `head_request`,
`informational`, `upgrade`, `closes`, `watched` and `sse_body` that `analyze`
owes, following `head_support.zig` and its tests:

- A bodyless response (a response to `HEAD`, 1xx, 204, 205, 304) has no body
  whatever its fields say.
- Two `Transfer-Encoding` fields, an empty one, `Transfer-Encoding` with
  `Content-Length`, an invalid length or two different lengths reject the
  head. Repeated equal lengths are one length.
- A final `chunked` coding means chunked. Any other coding closes a response
  and rejects a request.
- A response without a length closes. A request without one has no body.
- A status is exactly three digits from 100 to 599.
- `HEAD` in exact case marks a HEAD request. A watched request is a `POST`, in
  any case, to `/v1/messages` with or without a query.
- An SSE body needs one event-stream content type, identity content codings
  and at most plain `chunked` framing.

Around the analysis, the target checks how the head was read. A complete head
within `max_head_bytes` is consumed exactly, so the bytes after it stay
unread. The observer sees it once, and the other side receives it byte for
byte in one write. A head cut before its blank line, or longer than the bound,
is consumed up to EOF or the bound, reported to nobody and never written. A
failed write still reports the head and returns null. The `fill_bound` and
`over_bound` paddings build heads of exactly `max_head_bytes` and one byte
more.

`fuzz mutated heads` applies up to 8 `ByteEdit`s to a generated head, or takes
raw bytes, and checks what holds for any input. Reading stops right after the
first `CRLF CRLF` inside the bound, or at EOF or the bound without one. What
was read is reported once and forwarded unchanged. An accepted request has
status 0, is not informational, an upgrade or SSE, and is never
close-delimited. An accepted response has a status from 100 to 599, is never
a HEAD request or watched, has no body when bodyless, and closes when
close-delimited.

## Body contracts

`fuzz generated bodies` draws a `BodyShape` and then a payload of up to
4096 bytes. The shape picks the plan (`content_length`, `chunked`,
`until_close`, `none`), the direction, how the payload splits into chunks,
each chunk-size line (plain, uppercase, leading zeros, an extension, an
extension that fills `max_chunk_line_bytes` exactly), up to 4 trailers (one
fills the line bound exactly), a read schedule, a cut and a failing write.
A message with a declared end is followed by `NEXT-BYTES`.

Each generated body is relayed three times: in whole reads, in the shape's
schedule of 1 to 32 byte reads, and one byte at a time. The schedule wraps
`FakeSession` and sets `max_read_bytes` before each read. Every read returns
at least one byte or EOF, as `FakeSession` does. Each delivery owes the same
result:

- A complete message relays, consumes exactly the message and leaves
  `NEXT-BYTES` unread. It forwards the message byte for byte, reports the
  payload without chunk framing, and reports as body activity the payload plus
  two bytes per data chunk.
- A cut input fails for `content_length` and `chunked` and succeeds for
  `until_close`, where EOF ends the body. Either way it consumes and forwards
  exactly the bytes it had, and the reported payload is a prefix of the
  generated one.
- `none` consumes and forwards nothing.

Every fragment the observer sees must already be written, and no fragment may
carry more payload than the bytes it forwarded.

When the shape asks for a failing write, the target counts the writes of the
scheduled delivery and fails one of them. The relay must return false and make
no write after the failed one. What it forwarded and reported must be a prefix
of the message and payload, and it must not read past the message.

`fuzz mutated bodies` edits the encoded bytes, or takes raw ones, and checks
properties that need no oracle. The relay forwards exactly the prefix it
consumed and never reads past a declared length or skips input. A
`content_length` body relays only when the input holds the whole length, and
`until_close` consumes everything. The scheduled and one-byte deliveries must
agree with the whole-read delivery on the result, the bytes consumed, the
payload and the body activity.

## Corpus and budgets

The seeds are typed shapes, written by hand from the unit tests and the
source, each with the outcome it owes. The head target has 41 generated
seeds, 4 edited heads and 5 raw inputs. The body target has 14 generated
seeds and 9 edited or raw inputs. A seed test checks that the oracle agrees
with each written outcome, that the relay agrees with the oracle, and that
each seed's corpus encoding draws back to the same shape.

The bounds are named constants in each root: 8 header fields, a padding of up
to `max_head_bytes + 256`, 8 edits, 4096 payload bytes, 8 chunk splits, 4
trailers, 8 scheduled reads of at most 32 bytes. A comptime assertion keeps
each wire within `FakeSession`'s output. Every loop in the targets is bounded
by these constants or by the input length.

The generator stays inside forms the relay's tests already use. It never
writes whitespace before a field's colon, a length with a sign or an
underscore, or whitespace before a chunk extension's `;`. The mutation target
reaches such bytes but only checks the universal properties on them.

## Commands

`build/tests.zig` registers these steps through `build/fuzz_http1.zig`.
Run the seed corpora together, then fuzz one target per command:

```sh
zig build test-fuzz-http1 -Dgui=false -j1                  # httprelay tests + both seed corpora
zig build test-fuzz-http1-head -Dgui=false -j1 --fuzz=10K  # fuzz the head target alone
zig build test-fuzz-http1-body -Dgui=false -j1 --fuzz=10K  # fuzz the body target alone
```

Fuzz one target per command. `zig build --fuzz` runs every fuzz run step in
the graph at once, so `test-fuzz-http1 --fuzz` would fuzz head and body
together.

## Reading a campaign

With Zig 0.16.0 the limit applies to each fuzz test, and each target has two,
so `--fuzz=10K` runs about 20K inputs. The report names only the first fuzz
test of the step, but its counts cover the whole executable. Its coverage
counts program counters in the test runner, `std` and the relay together, so
it is not relay coverage. A short campaign without a failure shows that these
inputs found nothing. It does not show the relay has no bug.

A failure found while fuzzing does not change `zig build`'s exit status, so
read the output. The runner reports `input saved to '<cache>/f/crash'`. On
macOS that file came out empty once and truncated to 2048 of 2527 bytes
another time. The input is still in `<cache>/f/in<N>`: a little-endian header
of u64 `pc_digest`, u32 `instance_id`, u32 `test_i` and u32 `len`, followed by
`len` bytes of Smith input. Copy those bytes next to the target and read them
with `Smith{ .in = @embedFile(...) }` in a test to replay the failure without
`--fuzz`.
